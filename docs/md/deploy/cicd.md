# CI/CD

本文说明 Nilo 前端的持续集成与持续交付流程

> 注意：文中的 **GitHub 云服务器**指 GitHub Actions 执行任务时临时分配的运行环境；**服务器**指运行 Nilo 的机器

## 概览

| 阶段       | 触发方式                  | 现状                                                           |
| ---------- | ------------------------- | -------------------------------------------------------------- |
| CI         | 每次 push 与 Pull Request | 已完成：类型检查与打包；推送到 main 时保存构建产物；测试待补充 |
| CD         | 手动触发                  | 已完成：构建产物随提交自动保存，发布时只负责上传               |
| 发布后检查 | 发布完成后自动执行        | 已完成：冒烟检查，确认主站返回前端页面                         |

### 结构

```
推送到 main ──▶ CI（两个前端各自：安装依赖、类型检查、打包、保存产物）
手动触发 ──▶ 选择前端 ──▶ 获取当前提交的产物 ──▶ 上传 ──▶ 冒烟检查
```

两部分通过 GitHub Actions 的构建产物衔接：CI 负责构建，发布只取用产物，不再构建。

### CI

- 两个前端并行构建，互不影响，一个失败另一个照常跑完。
- 使用 `npm ci` 严格按锁文件安装依赖，比 `npm install` 更可重复。
- `npm run build` 包含 TypeScript 类型检查与 Vite 打包。
- 构建时注入环境相关的值，详见 [config.md](config.md)。
- 推送到 main 时，打包结果作为构建产物保存（每个前端一份，保留期为默认的 90 天），与发布无关。PR 与其他分支只做构建检查，不保存产物。
- 目前没有测试，构建通过只能说明类型和打包没有问题。
- CI 在一台干净的 Linux 机器上从零克隆代码运行：没有本地的 `.env`，没有被 git 忽略的文件，文件名区分大小写。本地能构建、CI 却失败的问题大多来自这些差异，见 [faq.md](faq.md)。

### CD

- 持续交付（Continuous Delivery）：每次提交到 main 都自动产出可直接上传的构建产物，发布时机由人工决定。
- 发布只取当前提交对应的产物并上传，不再构建。同一时间只运行一个发布任务，后触发的排队等待。
- 后续：支持按提交号发布与回滚。

### 发布后检查

发布完成后自动访问主站首页，详见下文。

## 操作

先把代码推送到 main 并等待 CI 完成，再在 GitHub Actions 中手动触发 Deploy 工作流，勾选要发布的前端：

| 选项       | 说明              | 默认 |
| ---------- | ----------------- | ---- |
| 用户端主站 | 发布 nilo-project | 勾选 |
| 后台管理站 | 发布 nilo-admin   | 勾选 |

> 注意：触发时选择的分支就是被上线的代码，请选择主分支。

## 发布流程

```
手动触发 ──▶ 选择与校验 ──▶ 获取产物 ──▶ 准备环境 ──▶ 上传 ──▶ 冒烟检查
```

全部步骤在同一个任务中完成，服务器只接收上传的文件。

| 步骤       | 作用                                                                  |
| ---------- | --------------------------------------------------------------------- |
| 选择与校验 | 汇总勾选项；一个都没勾选，直接失败                                    |
| 获取产物   | 找到当前提交在 main 上构建成功的 CI，下载所选前端的产物；找不到则失败 |
| 准备环境   | 写入上传用的 SSH 私钥；记录服务器的主机公钥                           |
| 上传       | 逐个前端：上传到服务器上对应的站点目录                                |
| 冒烟检查   | 访问主站，确认返回的是前端页面                                        |

### 获取产物

- 产物由 CI 在推送到 main 时构建，环境相关的值在构建时已经写入，详见 [config.md](config.md)。
- 找不到产物通常是 CI 还没跑完或失败了，或触发时选择的不是 main 上的提交。
- 发布使用的是已经构建好的产物，因此修改环境值（如 `MINIO_ENDPOINT`）后，必须重新运行 CI 构建，再发布。

### 上传

- 上传使用 `rsync`，只传输有差异的文件，并通过已有的 SSH 连接进行，不需要开放新的端口。
- 使用 `--delete` 使服务器目录与本次产物完全一致。产物的文件名带内容哈希，不删除旧文件会一直堆积。
- 上传账户的权限受到限制，详见 [security.md](security.md)。
- 上传后 nginx 立即提供新文件，不需要重启任何进程。

### 冒烟检查

请求主站首页，检查返回的内容中包含前端的挂载点（`id="app"`）。这同时验证了 nginx、证书和静态文件是否就位。

- 仅在配置了站点地址，并且本次发布了主站时执行。
- 后台站点限制了来源 IP，GitHub 云服务器无法访问，因此不检查后台。
- 只能发现页面打不开或返回的不是前端页面，发现不了运行时错误（如脚本报错导致白屏）。

## 新增前端应用的扩展方式

1. 新增应用目录，拥有独立的 `package.json` 与锁文件。
2. 在 CI 的构建矩阵中添加该应用。
3. 在发布工作流中添加勾选项，并指定它对应的站点目录。
4. 在服务器上为该应用增加站点目录与 nginx 站点配置。

## 取舍

| 决定                   | 原因                                              | 代价                                      |
| ---------------------- | ------------------------------------------------- | ----------------------------------------- |
| 手动触发               | 发布时机由人工控制                                | 多一次操作                                |
| 构建在 CI 中完成       | 每次提交都有可上传的产物，构建与发布解耦          | 每次推送到 main 都构建，占用 Actions 额度 |
| 在 GitHub 云服务器构建 | 服务器无需安装 Node.js 和源码，构建环境干净可重复 | 占用 GitHub Actions 额度                  |
| 构建时注入环境值       | 仓库与源码不含环境信息                            | 环境值变化后需要重新构建并发布            |
| 按应用选择性发布       | 只改了一个前端时不动另一个                        | 新增应用需同步维护                        |
| rsync 上传             | 只传差异，复用 SSH，无需新开端口                  | 不是原子替换                              |

## 当前的局限

- CI 仅做类型检查与打包，不运行测试。
- 发布只能使用当前提交对应的产物，且产物只保留 90 天，无法直接回到旧版本；回退方式是回退代码提交，待 CI 完成后重新发布。
- 上传不是原子的：上传的几秒内访问站点，可能遇到新旧文件混杂，刷新即可恢复。
- 冒烟检查只覆盖主站，且只检查页面能否返回。
